# 数据库概述

## 四大基本概念

| 概念          | 关键词              | 一句话定义       |
| ----------- | ---------------- | ----------- |
| **数据**      | 记录信息的符号          | 数据库中存储的基本对象 |
| **数据库**     | 长期存储、有组织、可共享     | 数据的集合       |
| **数据库管理系统** | 位于用户和 OS 之间      | 数据管理软件      |
| **数据库系统**   | 应用程序+DB+DBMS+DBA | 含人的整个系统     |

## 三级模式与二级映像

### 三级模式

| 模式  | 别名        | 层次  |
| --- | --------- | --- |
| 外模式 | 用户模式、子模式  | 用户层 |
| 模式  | 概念模式、逻辑模式 | 逻辑层 |
| 内模式 | 存储模式      | 物理层 |

### 二级映像

- 外模式/模式映像 → **逻辑独立性**
- 模式/内模式映像 → **物理独立性**

**判断技巧**：看到"表结构变了但应用程序不变"选逻辑独立性；看到"存储结构变了但模式不变"选物理独立性。

# 概念模型（ER 图）

## ER 图图形符号

| 图形 | 含义 |
|------|------|
| 矩形 | 实体 |
| 椭圆 | 属性 |
| 菱形 | 联系 |
| 下划线 | 键属性 |

## 联系类型判断

| 联系类型 | 判断关键词 | 示例 |
|----------|-----------|------|
| 1:1 | "一一对应" | 班级→班长 |
| 1: n | "一对多" | 班级→学生 |
| m: n | "多对多" | 学生↔课程 |

## 属性类型

| 类型 | 判断标准 |
|------|----------|
| 简单属性 | 不可再分（如学号） |
| 复合属性 | 可拆分（如地址→省/市/街道） |
| 单值属性 | 唯一取值（如学号） |
| 多值属性 | 多个取值（如电话号码） |
| 键属性 | 能唯一标识实体（下划线标识） |

## 键相关概念

- **超键**：能唯一标识实体的属性组（可冗余）
- **候选键**：超键的最小集（去掉任一属性就不再是超键）
- **主键**：从候选键中选一个

# 逻辑模型与关系模型

关系模型是最主流的一种逻辑模型。

## 关系术语

| 术语  | 含义        | 类比        |
| --- | --------- | --------- |
| 关系  | 一张二维表     | 整个表格      |
| 元组  | 一行        | 一条记录      |
| 属性  | 一列        | 一个字段      |
| 域   | 属性取值范围的集合 | 数据类型+取值范围 |
| 分量  | 元组中一个属性的值 | 单元格       |

## 规范化关系的性质

- 不允许重复元组
- 行序、列序无关紧要
- 分量必须是**不可分的数据项**（不能"表中有表"）

## 完整性约束

| 约束类型 | 关键词 | 核心内容 |
|----------|--------|----------|
| **实体完整性** | 主键 | 主键唯一且非空 |
| **参照完整性** | 外键 | 外键取值要么为空，要么等于被参照表的主键值 |
| **用户定义完整性** | Check/触发器 | 自定义业务规则 |

**参照完整性违约反应**：
- 级联删除（CASCADES）：删主表，从表一起删
- 受限删除（RESTRICTED）：从表有引用则不让删
- 置空值删除（NULLIFIES）：从表外键置 NULL

# SQL 语言

## 完整性约束的位置

| 约束位置 | 关键字 | 适用场景 |
|----------|--------|----------|
| 列级约束 | 紧跟列定义后 | 单列约束（如 NOT NULL） |
| 表级约束 | 所有列定义之后 | 多列主键、外键、多列 CHECK |

**快速判断**：PRIMARY KEY 如果是单列可在列级写，多列必须在表级写。

## SELECT 执行顺序

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

#### **WHERE** 不能使用聚集函数，**HAVING** 可以使用聚集函数筛选分组。

## LIKE 通配符

| 通配符 | 含义 |
|--------|------|
| `%` | 任意长度字符串（含 0 个） |
| `_` | 单个字符 |

**转义**：`LIKE 'DB\_%' ESCAPE '\'` 中的 `\_` 匹配下划线本身。

汉字为两个字符。

## 连接类型速记

| 连接类型 | 关键字 | 特点 |
|----------|--------|------|
| 内连接 | INNER JOIN / `,` | 只保留匹配的行 |
| 左外连接 | LEFT JOIN | 保留左表所有行 |
| 右外连接 | RIGHT JOIN | 保留右表所有行 |
| 全外连接 | FULL JOIN | 保留两表所有行（MySQL 不支持） |
| 自然连接 | NATURAL JOIN | 等值连接+去重 |

## 子查询关键词

| 谓词     | 含义      | 使用场景       |
| ------ | ------- | ---------- |
| IN     | 属于集合    | 返回多个值      |
| ANY    | 比某个值... | 子查询返回多值    |
| ALL    | 比所有值... | 子查询返回多值    |
| EXISTS | 存在      | 相关子查询，存在量词 |

**ANY/ALL 速记**：
- `> ANY` = 大于最小值
- `> ALL` = 大于最大值
- `< ANY` = 小于最大值
- `< ALL` = 小于最小值

可用 `NOT EXISTS` 达到全称量词效果。

## 集合操作

| 操作 | SQL 关键字 | MySQL 支持 |
|------|-----------|-----------|
| 并 | UNION | ✅ |
| 交 | INTERSECT | ❌（用 IN/EXISTS 代替） |
| 差 | EXCEPT | ❌（用 NOT IN/NOT EXISTS 代替） |

## 视图

| 要点 | 内容 |
|------|------|
| 视图本质 | 存储 SELECT 语句，不存数据 |
| WITH CHECK OPTION | 增删改不能破坏视图定义条件 |
| 可更新视图条件 | 不含 DISTINCT、FROM 单表、无 GROUP BY 等 |
| 不可更新视图 | 含分组/聚集函数/多表连接等 |

> **视图作用**：简化操作、逻辑独立性、安全保护、多角度看待数据。

# 数据库安全性

## 用户标识与鉴别

用户名/口令是**最常用**的用户标识与鉴别方法。

## GRANT 与 REVOKE

```sql
GRANT 权限 ON 对象 TO 用户 [WITH GRANT OPTION];
REVOKE 权限 ON 对象 FROM 用户;
```

**权限传播**：`WITH GRANT OPTION` 允许被授权者继续授予权限给他人。

## 可授权用户

只有以下用户能授予/收回权限：
1. **DBA**（数据库管理员）
2. **数据对象创建者**（属主）
3. **拥有传播权限的用户**（通过 WITH GRANT OPTION 获得）

## 角色

角色是**命名的权限集合**，用于简化授权管理。角色可以从属于别的角色（继承）。

# 完整性约束分类【!】

## 六类约束判断方法

| 约束类型 | **关键词** | 判断标准 |
|----------|-----------|----------|
| **静态列级** | 单列、当前值 | 一列当前值的范围/格式 |
| **动态列级** | 单列、变化前后 | 一列新旧值的关系 |
| **静态元组** | 单行、当前行内 | 同一行内多列间比较 |
| **动态元组** | 单行、变化前后 | 一行内新旧值的关系 |
| **静态关系** | 多行、当前 | 多行/多表间的关系 |
| **动态关系** | 多行、变化前后 | 多行/多表变化前后的关系 |

## 快速判断技巧

1. **先看涉及范围**：单列→列级；同一行多列→元组；多行/多表→关系
2. **再看是否涉及变化**：涉及新旧值→动态；只看当前值→静态

**例**："职务级别低的职工工资应低于职务级别高的职工工资" → 涉及多行比较，只看当前值 → **静态关系约束**

## CHECK vs 触发器

| 方式 | 适用场景 | 特点 |
|------|----------|------|
| CHECK | 静态列级、静态元组 | 简单条件，SQL 标准 |
| 触发器 | 动态约束、复杂业务逻辑 | Event-Condition-Action 模型 |

## 触发器要点

| 特性        | 说明                                    |
| --------- | ------------------------------------- |
| 触发时机      | BEFORE / AFTER / INSTEAD OF           |
| 触发粒度      | 语句级/ 行级，语句级效率更高                       |
| 触发事件      | INSERT、UPDATE、DELETE（**不能是 SELECT**！） |
| NEW / OLD | 引用新值和旧值                               |
| 触发方式      | **自动触发**，不能显式调用                       |

# 索引

## 存储器速度对比

| 存储器 | 访问速度 | 用途 |
|--------|----------|------|
| 内存 | 最快（~0.01μs） | 存放常用数据 |
| 磁盘 | 中等（~0.0025 s） | 存放业务数据 |
| 三级存储 | 最慢（~0.01 s） | 存放归档数据 |

## B+树索引要点

| 特点 | 说明 |
|------|------|
| 数据存放 | **所有数据（行 ID）存放在叶节点** |
| 叶节点 | 包含所有索引键+指向行的指针，形成链表 |
| 高度 | 一般 3 层，约 3 次磁盘 IO |
| 范围查询 | 效率高（叶节点链表） |
| 查询类型 | **I/O 密集型** |

**B+树 vs B 树**：B+树只在叶节点存数据 → 非叶节点可存更多索引项 → 树更矮 → I/O 更少；叶节点链表 → 范围查询更快。

## 散列索引

| 特点 | 说明 |
|------|------|
| 查询类型 | **CPU 密集型** |
| 等值查找 | 非常快（1 次 IO） |
| 范围查找 | ❌ 不支持 |
| 重复值 | 不适合重复值多的列 |
| 更新频繁 | 重构代价大，不适合 |

## 聚簇索引

| 特点 | 说明 |
|------|------|
| 物理顺序 | 表中数据物理顺序与索引顺序一致 |
| 数量限制 | 一张表**只能有一个**聚簇索引 |
| MySQL | 主键上自动建立聚簇索引 |
| 适用场景 | 范围查询、GROUP BY、ORDER BY |
| 不适用 | DML 频繁的表（维护开销大） |

## 联合索引

| 规则   | 说明                      |
| ---- | ----------------------- |
| 最左前缀 | 查询条件必须**包含**索引最左列才能使用索引 |
| 索引失效 | 对列进行函数运算/计算时索引失效        |

**示例**：索引 `(A, B)` 上：
- `WHERE A = 10` → ✅ 可用索引
- `WHERE B = 10` → ❌ 不可用索引
- `WHERE A*2 = 10` → ❌ 索引失效

## 索引选择原则

只在经常作为查询条件的字段上建索引。考虑因素：重复值占比、更新频率、是否范围/分组查询。

# 事务与并发控制

## ACID 特性

| 特性 | 含义 | 关键词 |
|------|------|--------|
| **原子性**（A） | 要么全做，要么全不做 | 不可分割 |
| **一致性**（C） | 事务前后数据库状态一致 | 总和不变 |
| **隔离性**（I） | 事务之间互不干扰 | 并发隔离 |
| **持久性**（D） | 提交后永久生效 | 不可撤销 |

## 事务状态

```
活动(Active) → 部分提交(Partially Committed) → 提交(Committed)
                                    ↓
                                 失败(Failed)
```

## 并发操作带来的问题

| 问题 | 关键词 | 冲突类型 |
|------|--------|----------|
| **丢失修改** | 后提交覆盖前提交的结果 | 写写冲突 |
| **不可重复读** | 两次读取结果不同 | 读写冲突 |
| **读"脏"数据** | 读取了未提交的数据 | 写读冲突 |

## 可串行化

- **可串行化**是并行事务正确性的**唯一准则**
- 冲突可串行化：通过调换**非冲突指令**顺序变为串行调度
- 前趋图有环 → 不可串行化；无环 → 冲突可串行化

## 封锁协议

| 封锁级别 | X 锁释放时机 | S 锁释放时机 | 解决的问题 |
|----------|-------------|-------------|-----------|
| 一级 | 事务结束 | 不加 S 锁 | 丢失修改 |
| 二级 | 事务结束 | 读完后立即释放 | 丢失修改、脏读 |
| 三级 | 事务结束 | 事务结束才释放 | 丢失修改、脏读、不可重复读 |

## 两阶段锁协议（2 PL）

| 阶段 | 操作 |
|------|------|
| 扩展阶段（Growing） | 只获得锁，不释放锁 |
| 收缩阶段（Shrinking） | 只释放锁，不获得新锁 |

**结论**：所有事务遵守 2 PL → 调度可串行化（充分非必要条件）
**2 PL 不能解决**：死锁、级联回滚

## 死锁

| 预防 | 诊断 | 解除 |
|------|------|------|
| 一次封锁法 | 事务等待图 | 选择一个事务回滚 |

# 数据库恢复

## 故障类型与恢复

| 故障类型 | 影响范围 | 恢复方法 |
|----------|----------|----------|
| 事务故障 | 只影响故障事务本身 | **UNDO**（撤销未提交事务） |
| 系统故障 | 所有正在运行的事务 | **UNDO + REDO** |
| 介质故障 | 内存+磁盘数据 | **后备副本 + REDO** |

## 日志类型

| 日志类型 | 记录内容 | 适用场景 |
|----------|----------|----------|
| Undo 日志 | 更新前的**旧值** | 事务回滚 |
| Redo 日志 | 更新后的**新值** | 已提交事务重做 |
| Undo/Redo 日志 | 旧值+新值 | No Force + Steal 模式 |

## Steal/Force 策略

| 组合 | 需要的日志 |
|------|-----------|
| Force + No Steal | 无需恢复 |
| No Force + No Steal | 需要 Redo |
| Force + Steal | 需要 Undo |
| **No Force + Steal** | **需要 Undo + Redo**（性能最好） |

## WAL 策略（Write-Ahead Logging）

**日志先写，数据后写**——保证故障时可恢复

## 检查点

检查点之前提交的事务**不需要恢复**。从检查点开始扫描日志，已提交的 REDO，未提交的 UNDO。

# 规范化理论

## 函数依赖相关概念

| 概念 | 定义 | 关键词 |
|------|------|--------|
| 完全函数依赖 | 决定因素的**所有属性**都需要 | 缺一不可 |
| 部分函数依赖 | 决定因素的**部分属性**即可推出 | 有冗余 |
| 传递函数依赖 | X→Y, Y→Z, Y↛X | 间接依赖 |

## 范式判断

```
1NF → 消除非主属性对码的部分依赖 → 2NF
2NF → 消除非主属性对码的传递依赖 → 3NF
3NF → 所有决定因素都包含候选码 → BCNF
```

### 快速判断法

1. **1 NF**：所有属性不可再分（一般默认满足）
2. **2 NF**：找非主属性，看是否有对码的部分依赖
3. **3 NF**：找非主属性，看是否有对码的传递依赖
4. **BCNF**：看所有函数依赖的左部是否都包含候选码

> **关键技巧**：
> - 若关系模式的**所有属性都是主属性**（全在候选键中），则至少满足 3 NF（因为无非主属性）。
> - 判断 BCNF 只看**函数依赖左部是否包含候选码**。

## 候选键求解方法

| 属性类别 | 判断依据 | 候选键命运 |
|----------|----------|-----------|
| **L 类** | 只在 FD 左边出现 | **必在**候选键中 |
| **R 类** | 只在 FD 右边出现 | **必不在**候选键中 |
| **LR 类** | 左右都出现 | 不确定，需尝试 |
| **N 类** | 左右都不出现 | **必在**候选键中 |

**步骤**：先求 L 类+N 类的闭包，若能推出全部属性即为唯一候选键；否则逐一加入 LR 类属性尝试。

## 模式分解判断

| 判断标准 | 含义 |
|----------|------|
| **无损连接性** | 分解后自然连接能还原原关系 |
| **保持函数依赖** | 所有函数依赖在分解中未丢失 |

### 快速判断技巧

- 无损连接：列表法看是否能出现全 `a` 行；二分解时检查 `R1∩R2 → R1-R2` 或 `R1∩R2 → R2-R1`
- 保持依赖：检查每个 FD 是否在分解后的依赖集中仍能推出

# 数据库设计

## 设计阶段速记

```
需求分析 → 概念设计 → 逻辑设计 → 物理设计 → 实施 → 运行维护
```

#### 新奥尔良法：需求分析、概念设计、逻辑设计、物理设计。

| 阶段 | 核心产出 | 关键词 |
|------|----------|--------|
| 需求分析 | 数据流图、数据字典 | 做什么 |
| 概念设计 | ER 图 | 信息结构（与 DBMS 无关） |
| 逻辑设计 | 关系模式（表） | 向关系模型转换 |
| 物理设计 | 索引、存储结构 | 存储结构与存取方法 |

## 需求分析

- **数据流图**：只反映数据处理和传送过程，与实际处理工具无关
- **数据字典**：数据项、数据结构、数据流、数据存储、处理过程

## 逻辑设计

### ER 图向关系模式转换【!】

| 联系类型 | 转换规则                              |
| ---- | --------------------------------- |
| 1:1  | 可合并到任一端；也可独立建表                    |
| 1: n | **合并到 n 端**（将 1 端主键加入 n 端）；也可独立建表 |
| m: n | **必须独立建表**，主键为两端主键组合              |

### 视图合并冲突

| 冲突类型 | 说明                   |
| ---- | -------------------- |
| 属性冲突 | 域冲突、单位冲突             |
| 命名冲突 | 同名异义、异名同义            |
| 结构冲突 | 同一对象不同抽象、属性不同、联系类型不同 |

## ORM

| 概念 | 说明 |
|------|------|
