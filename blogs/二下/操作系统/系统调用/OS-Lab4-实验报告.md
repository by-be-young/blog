# 思考题

## Thinking 4.1

> 思考并回答下面的问题：
> 
> - 内核在保存现场的时候是如何避免破坏通用寄存器的？
> - 系统陷入内核调用后可以直接从当时的 `$a0-$a3` 参数寄存器中得到用户调用 ` msyscall ` 留下的信息吗？
> - 我们是怎么做到让 sys 开头的函数“认为”我们提供了和用户调用 `msyscall` 时同样的参数的？
> - 内核处理系统调用的过程对 `Trapframe` 做了哪些更改？这种修改对应的用户态的变化是什么？

### 问题 1

通过观察 `include/stackframe.h` 中 `SAVE_ALL` 宏，不难发现，当程序需要暂时用寄存器存储数据的时候，使用的是 `$k0` 寄存器。这个寄存器是 MIPS 专门留给内核的，用户程序不能使用这两个寄存器。

因此，用户程序可能使用的其他所有寄存器均不会被更改。

### 问题 2

不可以。

在调用 `msyscall` 后，前四个参数会被存储在 `$a0-$a3` 寄存器中，但在 `SAVE_ALL` 的时候已经备份到了 `Trapframe` 中去了，之后的程序是可能修改这几个寄存器的值的。

### 问题 3

我们使用了已保存的 `Trapframe` 获得在异常发生时的现场，而不通过寄存器进行传参。

### 问题 4

1. 改变了 `cp0_epc` 的值：将其加 4，以跳过 `syscall` 这条已经执行过的指令。对应用户态中：从 `syscall` 的下一条指令继续执行。
2. 返回值存储在 `$v0` 中：存储系统调用的返回值。对应用户态中：可以获取系统调用的结果。

## Thinking 4.2

> 思考 `envid2env` 函数: 为什么 `envid2env` 中需要判断 `e->env_id != envid` 的情况？如果没有这步判断会发生什么情况？

查看 `include/env.h`：

```C
#define LOG2NENV 10
#define NENV (1 << LOG2NENV)
#define ENVX(envid) ((envid) & (NENV - 1))
```

可知，从 `envid` 获取下标的方式非常简单：就是获取 `envid` 的低 10 位即可。

这样的原理来自于构造 `envid` 的函数 `mkenvid`（位于 `kern/env.c`）：

```C
u_int mkenvid(struct Env *e) {
    static u_int i = 0;
    return ((++i) << (1 + LOG2NENV)) | (e - envs);
}
```

由此观之，即使有些页已经不要了，被覆盖成了新的页（即 `e - envs` 这一索引相同），旧页和新页的 ` envid ` 也是不同的。

因此，如果传入了错误的 `envid`，但恰好这个 `envid` 也能获取到其他条件都符合的进程控制块，不加以检查的话，后续就会犯大错。

## Thinking 4.3

> 思考下面的问题，并对这个问题谈谈你的理解：请回顾 `kern/env.c` 文件中 `mkenvid()` 函数的实现，该函数不会返回 0，请结合系统调用和 IPC 部分的实现与 `envid2env()` 函数的行为进行解释。

`mkenvid()` 函数不会返回 0，意味着不存在 `envid` 为 0 的进程。但是，`envid2env` 函数中却专门写了几行代码，来表示 `envid` 为 0 时的操作。

其实，这是一个精心的设计，正是因为没有为 0 的 `envid`，所以我们才能用 0 表示一个特殊的情况：当我们需要传入当前进程的 `envid` 的时候，不需要再传入 `curenv->env_id`，而是直接传入 0 这个参数即可。

这个方法不仅更加简洁，而且能够直接略过一些不必要的检查。毕竟操作进程自身一定是有效、安全的。

## Thinking 4.4

> 关于 fork 函数的两个返回值，下面说法正确的是：
> A、 fork 在父进程中被调用两次，产生两个返回值
> B、 fork 在两个进程中分别被调用一次，产生两个不同的返回值
> C、 fork 只在父进程中被调用了一次，在两个进程中各产生一个返回值
> D、 fork 只在子进程中被调用了一次，在两个进程中各产生一个返回值

答案是 C。

虽然只被调用了一次，但是竟然会产生 2 个不同的返回值。

1. 在父进程中，返回值为子进程的 `pid`；
2. 在子进程中，返回值为 0。

## Thinking 4.5

> 上述“最小版”策略要求你在遍历时跳过 `UXSTACK` 与 `UVPT/VPT/VPD` 等特殊区域。请结合 `kern/env.c` 中 `env_init` 的映射行为、`include/mmu.h` 的内存布局图，解释：
> 
> - 为什么子进程的 `UXSTACK` 必须重新分配，而不能共享或设为 COW？
> 
> - 为什么不应对 `UVPT/VPT/VPD` 等自映射区域调用 `duppage`？如果误处理，可能引发哪些不一致或错误行为？

### 问题 1

`UXSTACK` 是用户异常栈，在发生 TLB Mod 异常时会由内核移交给用户异常栈处理。

如果被设为共享，那么父进程和子进程在处理异常的过程中会相互干扰，发生错误；

如果被设为写时复制，那么在写入 `UXSTACK` 时又会发生 TLB Mod 异常，又要跳转到 `UXSTACK`，又发生异常……产生死循环！

### 问题 2

两个进程的页表应该相互独立。如果调用 `duppage`，会导致子进程的 `UVPT` 映射到的是父进程的页目录，而不是自己的页目录。

而硬件通过 MMU 查页表又是正确的，就会导致不一致。

## Thinking 4.6

> 在遍历地址空间存取页表项时你需要使用到 `vpd` 和 `vpt` 这两个指针，请参考 `user/include/lib.h` 中的相关定义，思考并回答这几个问题：
> 
> 1. `vpt` 和 `vpd` 的作用是什么？怎样使用它们？
> 2. 从实现的角度谈一下为什么进程能够通过这种方式来存取自身的页表？
> 3. 它们是如何体现自映射设计的？
> 4. 进程能够通过这种方式来修改自己的页表项吗？

### 问题 1

作用：在用户态下通过访问进程自己的物理内存获取用户页的页目录项页表项的 `perm`，用于 `duppage` 根据不同的 `perm` 类型在父子进程间执行不同的物理页映射；

使用：

`vpd` 是页目录首地址，以 `vpd` 为基地址，加上页目录项偏移数即可指向 `va` 对应页目录项，即 ` (*vpd) + (va >> 22) ` 或 ` vpd[va >> 22]`；

`vpt` 是页表首地址，以  `vpt` 为基地址，加上页表项偏移数即可指向 `va` 对应的页表项，即 ` (*vpt) + (va >> 12) ` 或 ` vpt[va >> 12]` 即 ` vpt[VPN (va)]`；

### 问题 2

存储页表的空间属于用户空间，因此用户进程可以通过指针取得页表的地址来进行访问。系统是线性地进行页面的映射，因此可以很方便地实现“虚拟地址->虚拟页号”的转变。

虚拟页号即虚拟地址对应的虚拟页面相对页表项的偏移量，获得了页表首地址和偏移量后，就可以获取对应的页表项。

### 问题 3

```C
#define vpt ((volatile Pte *)UVPT)
#define vpd ((volatile Pde *)(UVPT + (PDX(UVPT) << PGSHIFT)))
```

从这里可知，页目录地址 `vpd` 在 `UVPT` 和 `UVPT + PDMAP`，说明将页目录映射到了某一页表位置；通过 `vpt` 来找 `vpd`，这表明页表 `vpt` 中存在某一页为页目录，由此体现了自映射设计。

### 问题 4

不能。自映射页表区域对用户**只读**，不允许修改页表项。如果要修改，必须通过系统调用陷入内核。

## Thinking 4.7

> 在 `do_tlb_mod` 函数中，你可能注意到了一个向异常处理栈复制 `Trapframe` 运行现场的过程，请思考并回答这几个问题：
> 
> 1. 这里实现了一个支持类似于“异常重入”的机制，而在什么时候会出现这种“异常重入”？
> 2. 内核为什么需要将异常的现场 `Trapframe` 复制到用户空间？

### 问题 1

在处理因写入 COW 产生的 TLB Mod 异常的过程中，假如又需要写 COW 页面，就会发生“异常重入”

### 问题 2

和其他异常处理不同，这个异常是在用户态处理的，返回原位置的时候不会进行现场恢复。所以我们需要手动将内核态中保存的现场发给用户空间。

## Thinking 4.8

> 在用户态处理页写入异常，相比于在内核态处理有什么优势？

这就是微内核的设计思想。

1. 让内核代码尽量地少而简单，将复杂的复制页面工作交给用户态完成；
2. 内核态崩溃的影响严重，而用户态崩溃更容易解决，不会导致整个操作系统崩溃；
3. 用户态的权限较低，更不容易操作到非法地址。

## Thinking 4.9

> 请思考并回答以下几个问题：
> 
> 1. 为什么需要将 `syscall_set_tlb_mod_entry` 的调用放置在 `syscall_exofork` 之前？
> 2. 如果放置在写时复制保护机制完成之后会有怎样的效果？

### 问题 1

`syscall_exofork()` 返回后父子进程各自执行自己的进程，子进程需要修改 `entry.S` 中定义的 `env` 指针，涉及到对COW页面的修改，会触发COW写入异常，COW中断的处理机制依赖于 `syscall_set_tlb_mod_entry`，所以将 `syscall_set_tlb_mod_entry` 的调用放置在 `syscall_exofork` 之前；

### 问题 2

父进程在调用写时复制保护机制可能会引发缺页异常，而异常处理未设置好，则不能正常处理。

# 难点分析

## 用户态和内核态

本次实验中必须得要分清楚哪些是用户函数哪些是内核函数，因为二者的操作权限是不一样的。如果用户函数想要知道内核态中的信息（如进程控制块），则必须要进行系统调用。

系统调用能从用户态陷入内核态，在内核态中进行相应处理后返回用户态。

一种常见的错误就是在用户态中使用如 `page_alloc` 这样的内核函数，说明还没有完全理解用户态和内核态的区别。

## TLB Mod 异常的处理办法

我们实验中，对这个异常的处理十分奇怪：不是在内核态处理完异常，而是把核心功能交给用户态来处理。

这需要及时转换思维，不能延续系统调用这一异常的处理流程了。包括 `Trapframe` 的保存和复制等流程都与正常的异常处理不同。
