# 思考题

## Thinking 4.1

> 思考并回答下面的问题：
> 
> - 内核在保存现场的时候是如何避免破坏通用寄存器的？
> - 系统陷入内核调用后可以直接从当时的 `$a0-$a3` 参数寄存器中得到用户调用 ` msyscall ` 留下的信息吗？
> - 我们是怎么做到让 sys 开头的函数“认为”我们提供了和用户调用 `msyscall` 时同样的参数的？
> - 内核处理系统调用的过程对 `Trapframe` 做了哪些更改？这种修改对应的用户态的变化是什么？

### 问题 1

通过观察 `include/stackframe.h` 中 `SAVE_ALL` 宏，不难发现，当程序需要暂时用寄存器存储数据的时候，使用的是 `$k0` 寄存器。这个寄存器是 MIPS 专门留给内核的，用户程序不能使用这两个寄存器。

因此，用户程序可能使用的其他所有寄存器均不会被更改。

### 问题 2

不可以。

在调用 `msyscall` 后，前四个参数会被存储在 `$a0-$a3` 寄存器中，但在 `SAVE_ALL` 的时候已经备份到了 `Trapframe` 中去了，之后的程序是可能修改这几个寄存器的值的。

### 问题 3

我们使用了已保存的 `Trapframe` 获得在异常发生时的现场，而不通过寄存器进行传参。

### 问题 4

1. 改变了 `cp0_epc` 的值：将其加 4，以跳过 `syscall` 这条已经执行过的指令。对应用户态中：从 `syscall` 的下一条指令继续执行。
2. 返回值存储在 `$v0` 中：存储系统调用的返回值。对应用户态中：可以获取系统调用的结果。

## Thinking 4.2

> 思考 `envid2env` 函数: 为什么 `envid2env` 中需要判断 `e->env_id != envid` 的情况？如果没有这步判断会发生什么情况？

查看 `include/env.h`：

```C
#define LOG2NENV 10
#define NENV (1 << LOG2NENV)
#define ENVX(envid) ((envid) & (NENV - 1))
```

可知，从 `envid` 获取下标的方式非常简单：就是获取 `envid` 的低 10 位即可。

这样的原理来自于构造 `envid` 的函数 `mkenvid`（位于 `kern/env.c`）：

```C
u_int mkenvid(struct Env *e) {
    static u_int i = 0;
    return ((++i) << (1 + LOG2NENV)) | (e - envs);
}
```

由此观之，即使有些页已经不要了，被覆盖成了新的页（即 `e - envs` 这一索引相同），旧页和新页的 ` envid ` 也是不同的。

因此，如果传入了错误的 `envid`，但恰好这个 `envid` 也能获取到其他条件都符合的进程控制块，不加以检查的话，后续就会犯大错。
