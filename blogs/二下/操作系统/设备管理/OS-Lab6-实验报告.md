# 思考题

## Thinking 6.1

> 示例代码中，父进程操作管道的写端，子进程操作管道的读端。如果现在想让父进程作为“读者”，代码应当如何修改？

修改如下：

```c
switch (fork()) {
    case -1:
        break;
    
    case 0:
        close(fildes[0]); 
        write(fildes[1], "Hello world\n", 12);
        close(fildes[1]);
        exit(EXIT_SUCCESS);
    
    default: 
        close(fildes[1]); 
        read(fildes[0], buf, 100); 
        printf("father-process read:%s", buf); 
        close(fildes[0]); 
        exit(EXIT_SUCCESS);
}
```

## Thinking 6.2

> 上面这种不同步修改 pp_ref 而导致的进程竞争问题在 user/lib/fd. C 中的 dup 函数中也存在。请结合代码模仿上述情景，分析一下我们的 dup 函数中为什么会出现预想之外的情况？

原来的 dup 函数实现中，先通过 `fd_alloc` 分配新的文件描述符结构，然后调用 `dup` 映射文件内容，最后更新文件描述符的引用计数。如果在映射完文件描述符但尚未映射文件内容时进程被调度出去，另一个进程可能认为该文件描述符已经可用并尝试使用它，但由于文件内容尚未正确映射，会导致错误。正确的顺序应该是先映射文件内容，再映射文件描述符，确保文件描述符可用时底层资源已经就绪。

## Thinking 6.3

> 阅读上述材料并思考：为什么系统调用一定是原子操作呢？如果你觉得不是所有的系统调用都是原子操作，请给出反例。希望能结合相关代码进行分析说明。

从提供的代码片段可以看出，系统调用入口处通过 CLI 宏关闭了中断：

```asm
.macro CLI
        mfc0    t0, CP0_STATUS
        li      t1, (STATUS_CU0 | 0x1)
        or      t0, t1
        xor     t0, 0x1
        mtc0    t0, CP0_STATUS
.endm
```

操作系统在处理系统调用时首先关中断，因此系统调用本身具有原子性。但并非所有系统调用都是整体原子的，例如 `sleep` 系统调用可能会主动让出 CPU，此时内核会保存上下文并调度其他进程，这个过程中断是打开的，因此 `sleep` 不是一个原子操作。

> 仔细阅读上面这段话，并思考下列问题：

> 1. 按照上述说法控制 pipe_close 中 fd 和 pipe unmap 的顺序，是否可以解决上述场景的进程竞争问题？给出你的分析过程。
> 
> 2. 我们只分析了 close 时的情形，在 fd. C 中有一个 dup 函数，用于复制文件描述符。试想，如果要复制的文件描述符指向一个管道，那么是否会出现与 close 类似的问题？请模仿上述材料写写你的理解。

### 第一问

可以解决。先关闭 pipe 缓冲区并减少引用计数，此时即使发生中断，其他进程通过检查引用计数就能知道管道已处于关闭过程中，从而阻止后续的读写操作，避免了竞争条件。

### 第二问

可以解决。在 dup 过程中，应先建立底层资源（如 pipe 缓冲区）的映射，再建立文件描述符的映射。这样即使发生进程切换，新复制的文件描述符只有在底层资源完全就绪后才会被其他进程使用，保证了操作的正确性。

## Thinking 6.6

> 通过阅读代码空白段的注释我们知道，将标准输入或输出定向到文件，需要我们将其 dup 到 0 或 1 号文件描述符（fd）。那么问题来了：在哪步，0 和 1 被“安排”为标准输入和标准输出？请分析代码执行流程，给出答案。

在 `user/init.c` 中，通过以下代码完成标准输入输出的初始化：

```c
if ((r = opencons()) != 0) {
    user_panic("opencons: %d", r);
}
if ((r = dup(0, 1)) < 0) {
    user_panic("dup: %d", r);
}
```

首先调用 `opencons()` 打开控制台作为标准输入，其返回的文件描述符为 0；然后通过 `dup(0, 1)` 将标准输入复制到文件描述符 1，从而将标准输出也指向控制台。

## Thinking 6.7

> 在 shell 中执行的命令分为内置命令和外部命令。在执行内置命令时 shell 不需要 fork 一个子 shell，如 Linux 系统中的 cd 命令。在执行外部命令时 shell 需要 fork 一个子 shell，然后子 shell 去执行这条命令。
> 
> 据此判断，在 MOS 中我们用到的 shell 命令是内置命令还是外部命令？请思考为什么 Linux 的 cd 命令是内部命令而不是外部命令？

MOS 中的 shell 命令是外部命令，每个命令都通过 `spawn` 创建新进程执行。Linux 的 `cd` 命令是内部命令，因为它需要修改当前 shell 进程的工作目录，如果作为外部命令执行，子进程修改的只是自己的工作目录，父进程的工作目录不会改变，无法达到预期效果。

# 实验总结

Lab 6 是整个 MOS 操作系统实验的最后一个环节，主要完成了两个核心任务：Shell 命令解释器的实现和管道通信机制的完善。

在 Shell 的实现中，核心工作是解析用户输入的命令行，支持带参数的外部命令执行，以及输入输出重定向功能。通过实现 `runcmd` 函数，Shell 能够识别并处理各种命令格式，对于外部命令则通过 `spawn` 创建新进程来执行。管道功能的实现则涉及 `pipe` 系统调用、管道文件描述符的管理以及进程间的数据传递机制。管道本质上是一个内核维护的环形缓冲区，通过文件描述符的共享实现读写进程的同步与通信。

Lab 6 的完成意味着整个 MOS 操作系统已经具备了基本的多任务管理、文件系统、进程间通信和用户交互能力。从 Lab 1 的引导启动和内存管理，到 Lab 3 的进程管理，再到 Lab 4 的进程间通信和 Lab 5 的文件系统，最后到 Lab 6 的 Shell 与管道，每一步都是在前一阶段的基础上逐步完善，最终构建出一个能够运行用户程序并支持交互的小型操作系统内核。
